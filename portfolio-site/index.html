01Personal project · In active development

F1 AI

An agentic AI assistant for Formula 1, grounded in verified race data.

Problem. General-purpose chatbots answer Formula 1 questions from outdated training data and frequently misstate drivers, teams and results. Accurate data exists, but it is spread across historical race databases, timing feeds and FIA regulation documents. F1 AI is designed to answer only from data it has retrieved.

Approach. A custom agent loop selects from specialized tools — race analysis, lap-telemetry comparison, race prediction, read-only SQL over historical results and regulation search — and streams its progress to the interface as it works. If the primary model fails, requests fail over to a secondary model automatically.

Key challenge. Keeping answers consistent with the retrieved data. Even with correct data in context, the model occasionally attributed drivers to the wrong teams. I added three safeguards: aggregates computed in code rather than by the model, a grounding policy in the system prompt, and an automated checker that validates every driver–team claim and triggers a repair pass when one fails.

Development. I own the product, architecture and data design; implementation is carried out with AI coding agents, gated by automated tests and CI.

02

Arizona State University · Solo project

Elastic Face Recognition

A face-recognition service implemented on three AWS architectures.

Context. Built for a graduate cloud computing course at Arizona State University. The assignment was a single service — identifying faces in photos and video frames — implemented three ways: on virtual machines, on serverless functions and at the edge. Each version was evaluated by an autograder issuing 100 concurrent requests.

Approach. On EC2 (Fig. 3), a Flask web tier stores each upload in S3 and queues its key; up to 15 worker instances, launched from a custom PyTorch AMI, retrieve the image and run the course-provided recognition model. On Lambda, detection and recognition run as container images from Amazon ECR, since PyTorch exceeds Lambda’s package-size limit. At the edge, detection runs on an AWS IoT Greengrass device, which answers frames without faces locally instead of sending them to the cloud.

Key challenge. Elastic scaling without AWS Auto Scaling, which the assignment prohibited. I implemented a custom controller that reads queue depth every two seconds, counts in-flight requests as demand, starts worker instances to match, and lets each worker stop itself once the queue is empty.

AWS S3 · EC2 · SQS · Lambda · ECR · IAM · IoT Greengrass · Python · Flask · PyTorch · Docker · MQTT

WeVibe

An iOS dating app built around time-limited conversations.

Concept. WeVibe pairs two nearby users in a 24-hour chat with a limit of 20 messages each. The conversation becomes a match only if both users opt in.

My contribution. Developed most of the SwiftUI client — authentication, onboarding, profiles, photos, location, the matchmaking queue and chat — and extended the Node.js backend with photo uploads, location sync, push notifications, message pagination, Apple Sign-In token revocation and rate limiting for AI-generated bios.

04

Arizona State University · Solo project

Gotham Watch

A county-level crime analytics platform built on a knowledge graph.

Problem. FBI crime statistics are published as flat files keyed by numeric state and county codes, which makes straightforward questions — such as which offenses are most common in a given county — difficult to answer. Gotham Watch makes that data explorable through an interactive map and filters.

Approach. I cleaned four years of FBI county data (2011–2014) with pandas, modeled it with an OWL ontology as approximately 400,000 RDF triples, and loaded it into GraphDB on Azure. A Flask API translates each filter into a SPARQL query, and the React front end renders the results as a county heat map or a breakdown across seven crime categories.

Key challenge. Integrating two datasets with inconsistent county identifiers, including 310 FIPS codes missing their leading zero. I normalized both to a shared identifier scheme so related records resolve to the same graph node, without a join table.

React · Python · Flask · SPARQL · GraphDB · Azure

05

Hackathon project

MoneyNest

A game-based financial literacy platform with AI-guided feedback.

Problem. Financial education often fails to reach gig workers, students, immigrants, retirees and single parents. I proposed MoneyNest at a hackathon as a game-based alternative, available in English and Spanish, with XP and a shared leaderboard to encourage continued use.

Approach. Users begin with a conversation that Claude converts into a structured financial profile and health score. They then learn through three games: Wealth Farm, an investing simulation based on historical market data that ends with personalized feedback from Claude; Term Match, which pairs financial terms with their definitions; and FinWord, a Wordle-style vocabulary game.

Next.js · React · TypeScript · Vercel AI SDK · Claude · Zod · Supabase · Tailwind CSS
